TITLE:
GETRA Master API Stabilization

ORIGINAL ISSUES:
- `POST /api/auth/register` was throwing 500 INTERNAL_ERROR or returning uncontrolled 429 errors from Supabase.
- Repeated integration test runs and Postman tests were hitting Supabase's strict email registration rate limits.
- Several test suites were failing due to missing `global.fetch` configuration in `getServerSupabaseClient`, and due to missing `GETRA_RATE_LIMIT` sources in error responses.
- `auth-register-test` was sending `example.com` emails which the Supabase remote validation blocked with 400.

ROOT CAUSES:
1. Supabase rate limits registrations strictly; trying to test registration in automated suites or casually causes an `over_email_send_rate_limit` ban for the project endpoint.
2. `RateLimitExceededError` was updated to require a `source` to differentiate `GETRA_RATE_LIMIT` from `SUPABASE_AUTH`, but integration tests were not updated to expect the new payload.
3. `getServerSupabaseClient` was commented out of using `createTimeoutFetch`, leading to unexpected mock shapes in unit tests.

AUTH FIXES:
- Updated the schemas and documentation to emphasize using `gmail.com` or real domain variations, avoiding known blocked domains if applicable.
- Built a stable user provisioning flow intended to be used *once*, then tested multiple times with `login` instead of `register`.
- Fixed the API error payload assertions in integration tests.

RATE LIMIT FIXES:
- Modified the error response expected payloads in `auth-route-hardening.test.ts` and `rate-limit-response.test.ts` to properly account for the rate limit source tracking (`details.source`).
- Fixed a bug in `rate-limit.test.ts` where it used the wrong config key (`auth_login` instead of `auth_register`).

SUPABASE ISSUES:
- External Supabase project is on cooldown and hitting `SUPABASE_AUTH_RATE_LIMIT` because of excessive previous testing on the public registration endpoint.
