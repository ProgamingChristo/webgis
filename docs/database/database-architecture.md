# GETRA Database & PostGIS Foundation (Phase 4)

## Scope

Phase 4 defines database structure only. It contains no production UMKM,
transport, MAPID, survey, or research data. PostgreSQL migrations are the source
of truth.

## Architecture

```text
External source
  -> adapter
  -> Zod/geometry validation
  -> normalization to WGS84
  -> repository
  -> Supabase PostgreSQL + PostGIS
```

API routes must continue to use the existing authentication, authorization,
validation, service, and repository layers. Spatial filtering and distance
calculations run in PostGIS, not JavaScript loops.

## Tables

### `spatial_sources`

| Column | Type | Notes |
| --- | --- | --- |
| `id` | `uuid` | Primary key, generated by the database |
| `source_name` | `text` | Non-empty source/system name, such as MAPID |
| `source_type` | `text` | `external`, `survey`, `manual`, `imported`, or `system` |
| `description` | `text` | Optional description |
| `metadata` | `jsonb` | Object-only semi-structured metadata; credentials are prohibited |
| `created_at`, `updated_at` | `timestamptz` | Database-managed timestamps |

### `study_areas`

`id`, optional `source_id`, `name`, optional `description`, a required
`geometry(MultiPolygon, 4326)`, and timestamps. A `MultiPolygon` is canonical so
single and multipart study areas share one database type.

### `transport_corridors`

`id`, optional `source_id`, `name`, `transport_mode`, optional `description`, a
required `geometry(MultiLineString, 4326)`, and timestamps. Import normalization
must wrap a valid `LineString` as a one-part `MultiLineString` before persistence.

### `transport_nodes`

`id`, optional `source_id`, optional `corridor_id`, `name`, `node_type`,
`transport_mode`, a required `geometry(Point, 4326)`, and timestamps. A node is a
generic specific location and is not assumed to be a halte.

### `umkm_profiles`

`id`, required `owner_id`, optional `source_id`, `business_name`, `category`,
optional `description`, optional `address`, a required `geometry(Point, 4326)`,
and timestamps. `owner_id` references the existing `profiles.id` and prevents
deleting an owner while owned business data exists.

The nullable `source_id` fields are technical additions needed to preserve data
lineage without inventing source-specific columns.

## Relationships

- `study_areas.source_id -> spatial_sources.id`
- `transport_corridors.source_id -> spatial_sources.id`
- `transport_nodes.source_id -> spatial_sources.id`
- `transport_nodes.corridor_id -> transport_corridors.id`
- `umkm_profiles.source_id -> spatial_sources.id`
- `umkm_profiles.owner_id -> profiles.id`

Source and corridor deletion sets optional references to `NULL`. Owner deletion
is restricted to avoid accidental business-record loss.

## Geometry, CRS, and quality

All persisted geometry uses EPSG:4326. Typemods enforce the table-specific type
and SRID. `is_valid_wgs84_geometry` additionally rejects null/empty/invalid
geometry, unsupported geometry types, and coordinates outside longitude
`[-180, 180]` or latitude `[-90, 90]`. Geometry columns are also `NOT NULL`.

API and importer inputs should use the reusable GeoJSON Zod schemas in
`src/schemas/spatial.schema.ts`. PostGIS remains the final validation boundary.

## Indexes and query convention

Every geometry column has a GiST index. Foreign keys and expected categorical
filters have focused B-tree indexes; timestamps are intentionally not indexed
until an actual query pattern requires them.

Bounding-box queries should preserve the GiST-friendly operator and then apply
exact intersection:

```sql
select id, name
from public.study_areas
where geometry && public.make_wgs84_bbox(:min_lng, :min_lat, :max_lng, :max_lat)
  and st_intersects(
    geometry,
    public.make_wgs84_bbox(:min_lng, :min_lat, :max_lng, :max_lat)
  );
```

Distance between WGS84 points is available in meters:

```sql
select public.wgs84_distance_meters(:origin_point, :destination_point);
```

Future radius queries should use `ST_DWithin(geometry::geography, ..., :meters)`
with a caller-provided radius. Phase 4 defines no business radius.

## RLS

- Anonymous roles receive no privileges on Phase 4 tables.
- Authenticated users can read spatial reference tables.
- Only admins can insert, update, or delete spatial reference rows.
- UMKM owners can select, insert, and update their own rows.
- Other users cannot read or change owner rows.
- Admins can manage all Phase 4 rows.

Admin lookup uses `private.is_admin()`, a security-definer function outside the
Data API exposed schemas. Phase 4 also replaces the recursive Phase 2 admin
policies on `profiles` with this helper and hardens trigger search paths.

## Migrations, seed, and tests

The migration is
`supabase/migrations/20260815220000_create_spatial_foundation.sql`. The generated
`supabase/config.toml` pins the local PostgreSQL major version expected by the
current Supabase CLI.

`supabase/seed.sql` contains deterministic records named `TEST ...` only. Their
coordinates are synthetic and are not research or production data.

```bash
npm run db:start
npm run db:reset
npm run db:test
npm run db:lint
npm run db:migrations
```

Database tests cover PostGIS, geometry typemods/SRID, constraints, indexes,
foreign keys, point/line/polygon insertion, bbox/distance, and owner/admin RLS.

## Known limitations

- No production importer or MAPID adapter is implemented.
- No spatial business engine, routing, recommendation, or hard-coded radius is included.
- Direct verification of remote PostGIS/pgRouting needs a linked CLI session and
  PostgreSQL credentials. Phase 4 does not claim pgRouting is enabled.
- Reference-table read access is authenticated-only until product requirements
  explicitly require anonymous/public map access.
